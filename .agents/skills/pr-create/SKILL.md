# PR 생성 (pr-create)

현재 브랜치의 작업을 PR로 올린다. 핵심은 **이슈는 계획, PR은 실제 결과**라는 점이다. 개발 중 예상치 못한 문제로 구현이 달라졌다면 그 간극과 이유를 PR에 설명할 수 있어야 한다.

## 수행 절차

### 1. 의도 수집
- 예: "이 브랜치의 이름에 있는 이슈 번호를 확인하고, 이 브랜치에서 진행된 커밋을 확인해. 기능 개발이 완료되었다고 판단한다면 PR을 생성해줘."

### 2. gh 전제 조건
`references/gh-setup.md` 절차를 적용한다.
```
gh --version && gh auth status
```
- 없으면 설치 동의를 구하고 AI가 설치 → 인증 → 재개. 거부 시 PR 초안만 출력하고 종료.

### 3. 브랜치에서 이슈 번호 파싱
```
git branch --show-current
```
- `<type>/#<N>` 형식에서 이슈 번호와 type을 추출한다. (예: `feat/#6` → 6, `feat`)
- 번호가 없으면 사용자에게 질문한다.

### 4. push 상태 확인
PR은 원격 브랜치가 필요하다.
```
git status -sb
git rev-list --count @{u}..HEAD 2>/dev/null
```
- 미push 커밋이 있으면 push 동의를 구하고, 동의 시 `git push -u origin <branch>` 후 진행.
- 업스트림이 없으면 최초 push를 제안한다.

### 5. 커밋·변경 분석
```
git log main..HEAD --oneline
git diff main...HEAD --stat
```

### 6. 이슈 원문 조회
```
gh issue view <N> --json title,body
```
- 이슈의 요구사항·완료 조건·메커니즘을 확보한다.

### 7. 이슈 ↔ 구현 대조
- 이슈의 각 요구사항/완료 조건을 실제 변경과 **항목별로 대조**한다.
- 분류: **일치 / 부분 구현 / 다르게 구현 / 미구현**
- 각 차이에 대해 **커밋 본문의 why를 근거로 이유를 서술**한다.
- **커밋만으로 의도를 파악할 수 없는 차이는 추측하지 말고 사용자에게 직접 질문**한다.
  - 판단 기준: 커밋 본문에 설계 변경 이유가 없음 / 요구사항-구현 대응이 불명확 / 커밋들이 상충함
  - 질문 예: "이슈 #6의 「거리 기준 우선」이 실제로는 「시야각 기준」으로 구현된 것으로 보이나, 커밋에서 이유를 찾지 못했습니다. 어떤 이유로 변경됐나요?"
- 차이가 없으면 "이슈 계획대로 구현"으로 정리한다.

### 8. 완료 판단
- 미구현/부분 구현 항목이 있으면 사용자에게 알리고 확인한다.
- 미완성이면 `--draft` PR 또는 보류를 제안한다.

### 9. PR 초안 작성 및 확인
- `references/pr-template.md` 구조로 초안 작성(제목·본문, `Closes #N`, `## 이슈 대비 변경 사항`, Unity 검증 체크리스트 포함).
- **초안을 사용자에게 보여주고 확인**받는다.

### 10. PR 생성
```
gh pr create --base main --title "<제목>" --body-file <임시파일>
```
- 본문은 `--body-file`로 전달한다.
- 미완성이면 `--draft`.
- 생성된 **PR URL을 보고**한다.

## 주의사항
- "개발 완료" 판단은 근거(이슈 완료 조건 vs 커밋)와 함께 제시하고, 불확실하면 강행하지 않는다.
- 이슈와 다른 구현의 이유를 **임의로 지어내지 않는다.** 근거가 없으면 사용자에게 묻는다.
- 미push·미인증·미설치 상태에서 임의로 진행하지 않는다.
- PR 생성만 담당하고 병합은 하지 않는다.
